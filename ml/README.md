# Контекст навыков: первый ML-эксперимент

Цель — классифицировать контекст одного отмеченного упоминания навыка: обязательный, желательный или не требующийся. Это отдельная задача после извлечения названий технологий. Эксперимент не заменяет словарный алгоритм сайта и не подключён к пользовательскому интерфейсу.

## Запуск

Достаточно Python 3.10+; сторонних зависимостей, ключей API и доступа к сети нет.

```sh
python3 ml/experiment.py train
python3 -m unittest discover -s ml -p 'test_*.py' -v
python3 ml/experiment.py predict --text 'Знание Docker будет плюсом.' --skill Docker
```

Команды запускаются из корня JobLens. CLI принимает короткий контекст до 500 символов с одним точным вхождением указанного навыка. Значения меток: `required`, `optional`, `not_required`. Не передавайте полную вакансию с несколькими разными требованиями как один контекст.

## Данные и правила разметки

`data/context.jsonl` — 84 искусственно составленных русскоязычных фрагмента. Реальные вакансии, персональные данные и внешние корпуса не использованы. Источник каждой записи: `synthetic-authored`. Это начальный набор для разработки, не репрезентативная выборка рынка и не независимая экспертная разметка.

- `required`: есть явное требование, необходимость или обязанность применять навык.
- `optional`: навык даёт преимущество или приветствуется, но не является условием найма.
- `not_required`: явно сказано, что навык не нужен, исключён или не используется.

Нейтральные упоминания, неоднозначные фразы, противоречия и несколько требований в одном предложении пока не покрыты. В реальном наборе такие примеры нужно размечать отдельно, не принуждая их к одному из трёх классов.

Формат записи:

```json
{"id":"example-001","group_id":"source-001","split":"train","source":"synthetic-authored","text":"Нужен React.","skill":"React","start":6,"end":11,"label":"required"}
```

`start` и `end` — индексы Unicode-символов Python, конец не включается. Они не равны UTF-16 индексам JavaScript при наличии символов вне BMP. При будущей интеграции потребуется явное преобразование. `group_id` объединяет варианты одного источника или шаблона; все такие варианты должны оставаться в одной части данных.

В этом наборе каждый шаблон использован один раз. Split зафиксирован в данных: 60 примеров обучения (20 на класс), 24 проверки (8 на класс). Точные дубликаты после маскирования названия навыка и пересечения групп между частями запрещены. Похожие по смыслу формулировки остаются — один стиль составления может завышать оценку. Имена навыков заменяются на `targetskill`, чтобы алгоритм учился контексту, а не связи конкретной технологии с классом.

## Модель и сравнение

Multinomial Naive Bayes с Laplace smoothing `alpha=1`, признаками из слов и пар соседних слов. Словарь и параметры рассчитываются только на обучающей части. Гиперпараметры заданы до оценки; подбора по проверочным примерам нет.

Baseline для этой задачи — правило «каждое упоминание обязательно». Оно **не измеряет качество извлечения навыков** и не является оценкой precision/recall словарного распознавателя сайта. Для сравнения используется одна и та же задача контекстной классификации.

[REPORT.md](artifacts/REPORT.md) содержит accuracy, macro F1 и все ошибки. [report.json](artifacts/report.json) добавляет precision/recall/F1 каждого класса, матрицу ошибок (строки — истинный класс, столбцы — прогноз) и каждый прогноз. [model.json](artifacts/model.json) хранит параметры без исполняемой сериализации pickle. SHA-256 набора связывает отчёт с конкретными данными.

Начальный результат: macro F1 **0,584** у модели, **0,167** у постоянного baseline. Это результат на 24 синтетических примерах, а не доказательство полезности на реальных вакансиях. В частности, модель ошибается на некоторых отрицаниях и сложных формулировках. Логарифмические оценки нужны только для выбора класса; вероятность или confidence пользователю не выдаётся.

## Путь к подключению

1. Собрать разрешённые реальные фрагменты и расширить схему меткой для неопределённого контекста.
2. Разметить их по инструкции, провести независимую проверку разметки и решить разногласия.
3. Разбить по источникам/дубликатам до обучения. Выделить validation для настройки и закрытый test для итогового сравнения.
4. Сравнить этот baseline с линейной моделью и моделью языка на одинаковой выборке. Не изменять текущие тестовые метки ради лучшего результата.
5. Проверить отрицания, английский текст, списки, множественные упоминания и ошибки границ извлечения.
6. Только после этого подключать подсказку контекста к интерфейсу с подтверждением пользователя.

Содержимое `artifacts/` воспроизводимо командой обучения и может храниться в Git для воспроизведения эксперимента. При изменении модели обновляйте версию и отчёт. Коммиты — только после согласия владельца проекта.
