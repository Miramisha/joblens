# Вход по почте

В JobLens один сценарий регистрации и входа: email → шестизначный код → аккаунт. При первом подтверждении сервер создаёт пользователя и профиль; при следующих открывает тот же аккаунт. Пароли не используются. ChatGPT-заголовки полностью игнорируются.

## Подключить настоящую отправку

1. Создайте аккаунт [Resend](https://resend.com), добавьте свой домен отправителя и подтвердите предложенные DNS-записи. Для писем произвольным пользователям нужен подтверждённый домен; тестовый отправитель ограничен аккаунтом Resend.
2. Создайте API-ключ с правом отправки для этого домена. Не отправляйте ключ в чат.
3. Заполните локальную `.env`: `RESEND_API_KEY` и `EMAIL_FROM`, например `JobLens <login@your-domain.ru>`. Отдельный случайный `AUTH_SECRET` уже создан локально; он не попадает в Git. Для новой установки сгенерируйте 32 случайных байта в base64url: `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`.
4. Перезапустите `pnpm dev`. Незаполненная конфигурация отключает форму и возвращает 503 из API, коды не выводятся в браузер или логи.
5. Примените все SQL-миграции по порядку, включая `drizzle/0002_loving_alex_power.sql`. В основной локальной базе новая миграция уже применена.
6. Для production задайте `AUTH_SECRET` и `RESEND_API_KEY` как защищённые переменные Sites, `EMAIL_FROM` — как настройку отправителя. Используйте HTTPS. Внешний шлюз размещения также должен разрешать публичное открытие сайта, иначе до формы останется требование платформенного входа. Политика доступа и публикация в этой задаче не менялись.
7. После настройки проверьте доставку на собственную почту, ввод кода, повторный вход и выход. Локальная доставка на почту владельца Resend и ввод кода проверены: пользователь подтвердил почту и открыл личный аккаунт. Отправка другим пользователям требует подтверждённого домена и отдельно пока не проверена.

Письма отправляются сервером через [Resend Email API](https://resend.com/docs/api-reference/emails/send-email), с ключом идемпотентности на попытку доставки. Ошибки провайдера не раскрываются клиенту и не активируют код. Требования к отправителю: [Resend errors](https://resend.com/docs/api-reference/errors).

## Защита и хранение

- Код действует 10 минут, допускает 5 попыток, используется один раз. Проверка и погашение выполняются одним атомарным SQL-запросом.
- Новый код отменяет старый; запрос связан с HttpOnly cookie браузера. После обновления страницы можно снова запросить код, соблюдая минутный интервал.
- В базе хранится HMAC кода с отдельным серверным секретом, а также хеш случайного идентификатора запроса. Смена `AUTH_SECRET` отменяет ожидающие коды.
- Лимиты в D1 действуют для всех экземпляров сервера: 5 запросов на почту за часовое окно, 200 суммарно на сайт, не чаще одного письма в минуту на адрес. Отклонённые по cooldown запросы и неудачные доставки тоже расходуют лимит. Глобальный лимит защищает бюджет маленького проекта; перед ростом аудитории стоит дополнить его отдельным ограничением на уровне edge и настроить квоты.
- Cookie сессии: HttpOnly, SameSite=Lax, Secure на HTTPS, 30 дней. База хранит только хеш случайного токена. Выход отзывает текущую сессию и ожидающий запрос кода. Другие устройства остаются авторизованными.
- Запись требует same-origin Origin. Вход не раскрывает, был ли аккаунт зарегистрирован раньше. Истёкшие сессии, коды и лимиты очищаются при успешной отправке; срок проверяется независимо от очистки.
- Прежние платформенные аккаунты не связываются автоматически по email: для них не было сохранено проверенного email-владения. Их данные сохранены, но для переноса нужен отдельный подтверждённый процесс миграции. Новая регистрация создаёт отдельное пространство.

## Проверки без отправки писем

`pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`.

Интеграционные тесты запускаются только против localhost:3001 с отдельной базой `.wrangler/hh-test-state`. Примените к ней все три миграции через `wrangler d1 execute DB --local --config wrangler.local.json --persist-to .wrangler/hh-test-state --file <migration.sql>`. Затем запустите собранный Worker:

```
pnpm exec wrangler dev --config dist/server/wrangler.json --port 3001 --persist-to .wrangler/hh-test-state --var AUTH_SECRET:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA --var RESEND_API_KEY:test-not-a-real-key --var EMAIL_FROM:test@example.test --var HH_CLIENT_ID:test-client --var HH_CLIENT_SECRET:test-secret --var HH_REDIRECT_URI:http://localhost:3001/api/hh/callback --var HH_USER_AGENT:JobLens-test --var TOKEN_ENCRYPTION_KEY:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
```

Это только фиктивные тестовые ключи. Не используйте их для реальных данных.

```
python3 tests/email-auth-smoke.py
python3 tests/api-smoke.py
python3 tests/account-hh-smoke.py
```

`local_auth.py` записывает тестовые сессии и HMAC-коды напрямую в изолированную SQLite-базу. В приложении нет тестового способа входа. Проверяются активация, повторный вход, истечение, лимиты, replay, параллельная проверка одного кода, поддельные заголовки, cookie, Origin, выход и изоляция данных. Mail API отдельно проверяется с подставным HTTP-клиентом, без отправки писем.

В локальном Wrangler при сериях быстрых запросов иногда возникает инфраструктурный 503 «Your worker restarted mid-request». Это наблюдалось в smoke-тесте аккаунта; отдельный прогон проходит. Тесты не скрывают ответ повторной отправкой. Поведение размещённого Worker требует отдельной проверки после публикации.
